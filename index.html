Proving Ground user guide

Proving Ground lets you tune gameplay values while the game runs, keep the numbers you like as presets, and record runs so you can compare which settings played best. It works in the Editor's Play Mode and in development builds, and is off in release builds.

1. Quick start

  1. Install. Import the package, then check the Console is free of errors. It needs Unity 6 and no other packages.

  2. Mark some values. On any component, add using Exaweft.Proving;, put [Tune] on the fields you want to tune, and register the component while it is enabled:

    using Exaweft.Proving;
using UnityEngine;

public class PlayerMovement : MonoBehaviour
{
    [Tune("Movement", 1, 18, hint: "units/s")] public float speed = 10f;
    [Tune("Movement", 0, 3)] public int extraJumps = 1;
    [Tune("Cheats")] public bool godMode;

    void OnEnable()  => ProvingGround.Register(this);
    void OnDisable() => ProvingGround.Unregister(this);
}
  1. Tune. Press Play, then F1. Your values appear under "Movement" and "Cheats". Drag a slider and the game changes at once. Type a name under Presets and press Save to keep the values.
  2. See what happened. Press F2 for performance, counters, timers and events. Add your own anywhere: Diag.Count("Jumps");, Diag.Event("Boss phase 2");.
  3. Compare. Type a label in F2's Run section and press Start run; play; press End. Do the same with other settings and a different label, then press Compare runs… to see them side by side.

Changes made in Play Mode go when Play Mode ends, as usual in Unity (ScriptableObject assets included, see section 2). Save a preset to keep them, and copy the numbers you settle on into your scenes or assets.

To see all of this working before touching your own game, import the Basics sample (section 12).

2. Tuning values with [Tune] and registration

Mark fields with [Tune] and register the object. Supported types are float, int, bool and enums (not [Flags] enums). Fields may be public or private, but not static or readonly. Auto-properties work with [field: Tune], as long as they have a setter (a private one is fine); they appear under the property name. Values grouped in a struct or class, such as a Stats struct, are reached by marking both the field that holds it and the fields inside it (see "Values inside a struct or class" below).

public class PlayerMovement : MonoBehaviour
{
    [Tune("Movement", 1, 18, step: 0.5f, hint: "units/s")]
    public float speed = 10f;

    [Tune("Movement", 0, 3)]
    public int extraJumps = 1;

    [Tune("Cheats")]
    public bool godMode;

    void OnEnable()  => ProvingGround.Register(this);
    void OnDisable() => ProvingGround.Unregister(this);
}
  • Group, label and hint. The first argument is the panel group ("General" if left out). The label is made from the field name (extraJumps becomes "Extra jumps") unless you pass label:.
  • Range and step. Values set from the panel, a preset or code are clamped to the range given by min and max. Ints keep to whole numbers inside it. The step is used by the −/+ buttons and slider snapping; leave it out and it is 1 for ints and a hundredth of the range for floats. Not-a-number and infinite values are replaced by the default.
  • Defaults. The value a field holds when its object is first registered is its default, and Reset returns to it.
  • Starting values outside the range. If a field starts outside its range (or at infinity, or NaN), Proving Ground leaves it exactly as your game set it and logs one warning naming the field, its value and the range. The slider shows the nearer end; Reset returns to your value; anything set from the panel stays within the range. Widen the range, or fix the starting value, to make the warning go. An enum holding a value that isn't one of its members can't be shown, so it becomes the first member, also with a warning.
  • Shared values. Every registered object of a type shares one value per field: changing the speed changes it on every registered PlayerMovement, and one registered later starts with the current value.
  • Values of its own. To tune one object apart from the others of its type, such as one of two spawners, register it with a scope name: ProvingGround.Register(this, "Left spawner"). Objects with the same scope share values; the panel shows each scope as its own group ("Spawner · Left spawner"), and presets keep its values under the name, so use one that stays the same between sessions. [DebugAction] buttons in a scoped group run on that scope only.
  • Remembered values. When the last object with a field unregisters, its value is remembered and given to the next object that registers, such as after a scene reload. A new Play session starts afresh.
  • Any class. Register accepts ScriptableObjects and plain C# objects as well as components. Registration is explicit; Proving Ground never scans your scenes.
  • Assets are put back. Unity throws away changes to scene objects when Play Mode ends, but not changes to assets. So that tuning a ScriptableObject asset (an item, a building, an enemy type) never leaves it changed, Proving Ground puts each asset's tuned fields back to the values they had before it registered, once the Editor is back in Edit Mode. To keep values you like, save a preset. Fields without [Tune] are left as they are.
  • Values your game copies. Proving Ground changes the field. If your game copies the field somewhere else once, such as into a private variable in Awake or into a physics component at start-up, changing the field does nothing until the game reads it again. Tune the field the game reads while playing, or reapply the value when it changes (see ValueChanged below).

Values inside a struct or class

Mark the field that holds the struct or class, and each field inside it you want to tune:

public class Kart : MonoBehaviour
{
    [Tune("Handling")]
    public Stats stats = new Stats { topSpeed = 10f, grip = 0.95f };

    [System.Serializable]
    public struct Stats
    {
        [Tune(null, 1, 30, hint: "m/s")] public float topSpeed;
        [Tune(null, 0, 1)] public float grip;
    }

    void OnEnable() => ProvingGround.Register(this);
    void OnDisable() => ProvingGround.Unregister(this);
}
  • Group and label. A field inside uses its own group, or else the group given on the field that holds it. A label: on the holding field is put in front of each label inside ("Boost · Top speed"), which tells apart two fields of the same type.
  • Keys. Presets and run records name the value through the holding field: Kart.stats.topSpeed.
  • Structs are changed by copying, changing and storing back the whole struct, so code holding its own copy of the struct won't see the change; read it from the field. Classes are changed in place. A class that is null reads as zero and ignores changes, with a warning, until it exists; fields serialized by Unity are never null.
  • Depth. Up to four structs or classes deep. Unity objects, collections (arrays and lists) and strings can't hold tuned values.

Fields that can't be tuned are skipped with a warning in the Console naming the field and the reason.

From code, ProvingGround.Tuning lists every value (Values, Find(key)) and resets them (ResetAll, ResetGroup, or Reset on one value). Its ValueChanged event reports changes made through Proving Ground:

ProvingGround.Tuning.ValueChanged += value =>
{
    if (value.Key == "MyGame.Player.gravityScale") body.gravityScale = (float)value.Value;
};

3. Presets

ProvingGround.Presets saves and loads named sets of values as JSON files:

ProvingGround.Presets.Save("Fast enemies", out string message);
ProvingGround.Presets.Load("Fast enemies", out message);
IReadOnlyList<string> names = ProvingGround.Presets.List();
  • Files go to ProvingGround/Presets under Application.persistentDataPath. Set Presets.Directory to keep them somewhere else, such as a project folder under source control.
  • Names may use letters, digits, spaces, hyphens and underscores, up to 64 characters.
  • Loading sets every value in the file and returns values the file doesn't mention to their defaults, so a preset always gives the same result. Values for objects that haven't registered yet are applied when they do.
  • A save writes a temporary file first, so a failed save leaves the previous preset intact. Damaged, oversized or unrecognised files are refused without changing anything, and each call returns a message saying what happened.

4. The F1 panel: hotkeys, layout and [DebugAction] buttons

In the Editor and in development builds, press F1 in Play Mode to show or hide the panel. It lists every registered value by group, with the group's [DebugAction] buttons at the top.

  • Rows. Numbers with a range have −, a slider, + and a box for an exact number (Enter commits it; a value outside the range is clamped and the status line says so). The slider and the −/+ buttons snap to the step. Numbers without a range drop the slider. Bools show an On/Off button; enums step through their names. A value that differs from its default shows its name in amber, and its Reset button returns it.
  • Groups and search. Click a group's heading to collapse it. The search box filters by name, hint and group; the × inside it (and inside the other text boxes) clears it.
  • Placement and size. Left, Right and Float choose where the panel sits; drag a floating panel by its title. A− and A+ change its size. Until you press them, the panels start at their designed size on screens up to 1080 pixels high and larger in proportion above that (twice the size at 2160). These choices, and collapsed groups, are remembered in PlayerPrefs.
  • Presets. Type or pick a name, then Save, Load or Delete (Delete asks for a second press).
public class Player : MonoBehaviour
{
    [DebugAction("Testing", "Restore health", hint: "fills shield and hull")]
    void RestoreHealth() { /* game code */ }

    void OnEnable()  => ProvingGround.Register(this);
    void OnDisable() => ProvingGround.Unregister(this);
}

[DebugAction] methods take no parameters and may be private. A button runs its method on every registered object that has it; an exception is logged to the Console and reported on the status line.

From code:

ProvingGround.Panel.ToggleKey = KeyCode.BackQuote;   // KeyCode.None turns the hotkey off
ProvingGround.Panel.Title = "My Game";
ProvingGround.Panel.Open();

Default placement. If your game's own HUD sits where the panels would, choose their starting sides from code, for example in a bootstrap component's Awake:

ProvingGround.Panel.DefaultPlacement = PanelPlacement.Right;
ProvingGround.DiagnosticsPanel.DefaultPlacement = DiagnosticsPlacement.Right;  // F2 beside F1, both on the right

A default applies until someone picks a placement with the panel's buttons (or you set Placement); the pick is remembered and wins from then on. ForgetPlacement() returns a panel to its default. The F2 panel's own buttons are Auto (opposite the F1 panel, the default), Left and Right. When both panels are docked on the same side and open, F2 sits beside F1 instead of on top of it.

The panels are UI Toolkit, and Unity always draws OnGUI (IMGUI) on top of UI Toolkit, so a game's own OnGUI text shows through them. Skip it while a panel is open if it gets in the way, for example if (ProvingGround.DiagnosticsPanel.IsComparisonOpen) return; at the start of OnGUI.

The hotkey works with the Input System package and with the legacy Input Manager. Function keys stay live while typing; other hotkeys are ignored then so they can be typed. Esc ends typing in a panel box.

The panel draws on its own UI Toolkit panel settings above the game's UI, with no style sheets or fonts of its own (it uses Unity's built-in runtime font), so it doesn't affect the game's UI. Nothing is built until the panel is first opened.

5. Diagnostics: Diag.Event, Diag.Count, Diag.Timer, performance and logs

Record what happens from anywhere in game code. Press F2 in Play Mode to see it live.

using Exaweft.Proving;

Diag.Event("Boss phase 2");            // timestamped, shown in recent events and written to the log
Diag.Count("Deaths");                  // counters add up; Diag.Count("Coins", 5) adds 5
using (Diag.Timer("Path search"))      // times the work inside the block
{
    FindPath();
}

// A span across frames, such as a lap: keep the timer and dispose it when the span ends.
DiagTimer lap = Diag.Timer("Lap");
// ... later
lap.Dispose();
  • Cost. Counting and timing don't allocate after a name's first use, so they can run every frame. Events are written to the log, so keep them to things worth reading later. In release builds every call returns at once.
  • The F2 panel docks opposite the F1 panel by default (see section 4 to change it) and shares its size. It shows live and session frame rate, frame times (mean, 95th percentile, longest), memory and garbage collections, then counters, timers and the latest 32 events, newest first. A gap of over a second between frames (the Editor in the background, a breakpoint, a stalled load) is counted as a pause and kept out of the frame times; the summary lists pauses separately. Copy summary puts a readable report on the clipboard; Open logs opens the log folder.
  • Logs. One readable text file per Play session (or per run of a development build), opened the first time something is recorded, so a session that records nothing leaves no file. It starts with the build, platform and hardware, lists events, tuning changes made through Proving Ground (one line per value once it has gone a second without changing, with its final value and the time of the last change, so a slider drag is one line), preset loads, scene loads and run starts and ends, and closes with the same summary as Copy summary. Each file is capped at 2 MB, with room always kept for the summary, and the newest 20 files per game are kept.
  • Where. ProvingGround/Logs/Playtest under Application.persistentDataPath. Automated runs go to ProvingGround/Logs/Automated instead, so test bots can't rotate playtest logs away. A run counts as automated in batch-mode Unity, with the -provingground-automated command-line argument, or after Diag.MarkAutomated(true). Change the folder with ProvingGround.Diagnostics.LogDirectory and the file-name prefix (the product name by default) with LogFilePrefix, before the first diagnostics call.

From code, ProvingGround.Diagnostics gives the same data: Counters, Timers, RecentEvents, Performance, Summary(), CopySummary(), OpenLogFolder(), LogFile and LogStatus. ProvingGround.DiagnosticsPanel has ToggleKey (F2), Open, Close, Toggle, IsOpen and the placement settings above.

6. Run records and comparison

A run is a stretch of play with a label: one attempt at a level, one lap, one bot round. When it ends, Proving Ground saves a run record linking the exact settings it started with to what happened, so you can see which settings played best.

ProvingGround.Runs.Start("Evade");                    // label: runs are grouped by it when compared
ProvingGround.Runs.Start("Fast", preset: "Fast");     // load a preset first, so the run starts with exactly its values
ProvingGround.Runs.End("player destroyed");           // the outcome, saved with the record
  • Starting a run. From code as above; from the F2 panel (type a label in the Run section and press Start run or Enter); or on every scene load, with ProvingGround.Runs.AutoStartOnSceneLoad = true (set it in Awake; the run is labelled with the scene's name). Starting a run ends the one before it, and the end of Play Mode (or the build quitting) ends the last one. If a preset can't be loaded, the run doesn't start and the Console says why, so a bot never records a run with the wrong settings.
  • What a record holds. Run ID, label, batch, preset (marked "modified" if values changed after it was loaded), how the run started and why it ended; every setting at the start and at the end; settled changes during the run (one per value, as in the log) and preset loads; counters, timers and up to 200 events from the run alone; its duration and frame rate; and the build, Unity version, platform and scene. Times are seconds since the run started. Diag calls don't change: while a run is going, what they record counts for the run as well as the session.
  • Batches. Runs.BeginBatch("Jump test") tags every run started until Runs.EndBatch(), so a bot's runs can be found together (section 7). A batch is identified by its name alone, so Latest batch selects every saved run with that name, including runs from earlier batches that used the same name. To compare one batch on its own, give each a distinct name (for example with the date or a number), or clear out or move the older run records first.
  • Comparing. In F2, press Compare runs…. Saved runs are listed newest first; click runs to select them, or press Latest batch (from code, ProvingGround.DiagnosticsPanel.OpenComparison(selectLatestBatch: true) opens it with the latest batch selected, which is handy at the end of a scripted batch). Selected runs are grouped by label, one column per label, showing the number of runs, duration, each counter and timer (the mean per run with the range in brackets; a counter a run never used counts as 0), frame rate and frame times, then only the settings that differ between groups (or within one, as "mixed"). Copy comparison copies it as aligned text. The screen's own A− and A+ change only its text size (75% to 200%, remembered, and on top of the F1 panel's size); ProvingGround.DiagnosticsPanel.ComparisonTextSize sets it from code. RunComparison.Compare(records) gives the same rows, and ToText() the same text.
  • Reading a comparison. It shows each group's mean and range, not run-by-run differences, and it doesn't test whether a difference is real or chance. With a handful of runs, look at the ranges: if they overlap, play more runs before deciding. To compare settings round by round (the same level seed under two presets, say), the run records have what you need: ProvingGround.Runs.LoadAll() gives every record, and each one's label, batch, counters and duration.
  • Files. One JSON file per run, in ProvingGround/Runs/Playtest or …/Automated under Application.persistentDataPath (by the same rule as the logs). The newest 500 per game are kept in each folder. Change the folder with ProvingGround.Runs.Directory. ProvingGround.Runs.LoadAll() reads them back, newest first, skipping damaged files; the format is documented on RunRecord and carries a version number.

7. Scripted runs

Runs can be driven entirely from code: a test script plays the same round several times under each of a few presets, and the comparison shows how the presets did. The script plays the game; Proving Ground loads the presets, records each round and compares them. Proving Ground doesn't include bots or strategies; the script that plays your game is yours, because only your game knows what "playing" means.

The Basics sample (section 12) includes RunBatch, a short, reusable coroutine for this. Copy it into your project:

// Three rounds under each preset, alternating presets; each round is a run labelled with its preset.
StartCoroutine(RunBatch.Play("Jump test", new[] { "Low jump", "High jump" }, 3, PlayOneRound));

IEnumerator PlayOneRound(RunBatch.Round round)
{
    var random = new System.Random(round.Seed);      // the same seed for every preset in this round
    ResetLevel(random);
    yield return new WaitUntil(() => levelFinished);
    round.Outcome = playerWon ? "won" : "lost";        // saved with the run
}

Without the helper, the same thing is a few lines:

ProvingGround.Runs.BeginBatch("Jump test");
foreach (string preset in new[] { "Low jump", "High jump" })
    for (int i = 0; i < 5; i++)
    {
        ProvingGround.Runs.Start(label: preset, preset: preset);
        yield return PlayOneRound();
        ProvingGround.Runs.End("round over");
    }
ProvingGround.Runs.EndBatch();
ProvingGround.DiagnosticsPanel.OpenComparison(selectLatestBatch: true);   // show the result

What makes scripted runs worth comparing:

  • Make rounds repeatable. Give each round number a seed and use it for anything random, so every preset meets the same conditions and only the settings differ. Simulating in fixed steps rather than per frame, as the sample's runner does, keeps results the same at any frame rate.
  • Let the script make mistakes. A perfect script only shows differences in speed. To compare how settings feel (handling, difficulty), have it react late or imprecisely, the same way for every preset.
  • Count what matters. Diag.Count("Stumbles") or Diag.Count("Hits taken") inside the round puts a column in the comparison, which often explains why one preset was slower.
  • Run batch-mode tests from the command line. In batch-mode Unity, runs and logs go to the Automated folders, so they never push playtest records out.

8. Keeping game input away from the panels

The panels can be clicked and typed into while the game is running, so a game may need to ignore input meant for them. Proving Ground never reads or blocks your game's input itself; these properties tell your code when to:

PropertyTrue while
ProvingGround.IsPointerOverPanelsthe pointer is over either panel or the comparison
ProvingGround.Panel.IsTypinga Proving Ground text box (search, a number, a preset name, a run label) has the keyboard
ProvingGround.Panel.IsOpen, ProvingGround.DiagnosticsPanel.IsOpen, IsComparisonOpenthat panel is shown

Clicks. Ignore a click or tap that lands on a panel:

if (Input.GetMouseButtonDown(0) && !ProvingGround.IsPointerOverPanels) Shoot();          // Input Manager
if (Mouse.current.leftButton.wasPressedThisFrame && !ProvingGround.IsPointerOverPanels) Shoot();  // Input System

The scroll wheel. Scrolling a panel's list also turns the mouse wheel your camera may be reading:

float zoom = ProvingGround.IsPointerOverPanels ? 0f : Input.GetAxis("Mouse ScrollWheel");

Keyboard. Typing "12" into a number box would also press 1 and 2 in your game. Skip gameplay keys while typing:

if (!ProvingGround.Panel.IsTyping && Input.GetKeyDown(KeyCode.Alpha1)) SelectWeapon(1);

With the Input System and actions, the simplest way is to switch your gameplay action map off while typing:

void Update()
{
    bool typing = ProvingGround.Panel.IsTyping;
    if (typing && gameplay.enabled) gameplay.Disable();
    else if (!typing && !gameplay.enabled) gameplay.Enable();
}

Clicking in the game, or pressing Esc, ends typing.

A locked cursor. Games with mouse look usually lock and hide the cursor, which leaves the panels unclickable. Either let Proving Ground free it while a panel is open:

ProvingGround.FreeCursorWhileOpen = true;   // set it at startup, for example in Awake

It frees the cursor when the first panel opens and puts back how it was when the last one closes, unless your game changed the cursor meanwhile, in which case your game's setting stands. It acts only as panels open and close, so a game that locks the cursor every frame, or on any click, still needs its own check:

bool panels = ProvingGround.Panel.IsOpen || ProvingGround.DiagnosticsPanel.IsOpen;
if (!panels && Input.GetMouseButtonDown(0)) Cursor.lockState = CursorLockMode.Locked;

Also skip mouse look while a panel is open, or the view turns as you drag a slider.

UI navigation. With an EventSystem in the scene, the arrow keys and WASD move UI focus; Proving Ground stops them moving focus into its own text boxes, so they keep driving your game.

9. Release builds and performance

Proving Ground is on in the Editor and in development builds (Development Build ticked in the build profile) and off in every other build. ProvingGround.IsEnabled says which. Off means the API is still there, so game code compiles and runs unchanged, but nothing happens:

  • ProvingGround.Register returns 0 without looking at the object;
  • the panels don't open and nothing listens for F1 or F2 (there is no panel object at all, so no per-frame work);
  • Diag calls return at once, and runs don't start;
  • presets list as empty, and Save, Load and Delete return false;
  • nothing is written: no logs, run records, presets or PlayerPrefs.

Opening a panel while it's off logs one line saying why, once per session.

Playtest builds. To keep Proving Ground in a build that isn't a development build, such as one sent to testers, add PROVING_GROUND_PLAYTEST to that build profile's Scripting Define Symbols (Player settings, or the profile's own settings in Unity 6 Build Profiles). Make a separate profile for it so the release profile stays clean. PROVING_GROUND_OFF turns it off everywhere, including the Editor and development builds; it wins over the playtest define. Builds you send to testers are unsigned, like any Unity build, and some antivirus programs flag unsigned programs they haven't seen before; that applies to the build as a whole, not to Proving Ground.

Cost while the panels are closed. Using Proving Ground the usual way (registered values, a counter and a timer every frame), development and playtest builds allocated nothing over 600 frames with the panels closed, and release builds allocated nothing either. Diag.Event writes to the log, so keep events to things worth reading rather than calling it every frame.

Code stripping. Proving Ground finds [Tune] fields and [DebugAction] methods by reflection. In IL2CPP builds at every managed stripping level up to High, they were kept, including a [DebugAction] method nothing else calls. No link.xml is needed.

What ships. The package's runtime assembly (Exaweft.Proving.dll) is in every build, because game code refers to it; the Editor and test assemblies never are.

11. Known limitations

  • Supported field types are float, int, bool and enums (not [Flags]), in fields or auto-properties with a setter, directly or up to four structs or classes deep. Arrays, lists and other collections can't be tuned, so a list of per-level stats isn't reachable; nor can static, readonly, double, long, string, vector or colour fields. Unsupported fields are skipped with a Console warning.
  • One value per field per type. Objects of one type share a value unless registered with a scope (section 2).
  • Values copied at start-up don't follow tuning until the game reads the field again (section 2).
  • Game input isn't blocked for you. Your game decides when to ignore input meant for the panels (section 8).
  • The comparison shows means and ranges per label, not round-by-round differences or statistical tests (section 6).
  • Changes aren't written into scenes or prefabs. Save presets, and copy the values you choose into your project.
  • Panels draw above the game's UI Toolkit UI but below OnGUI (IMGUI) text, which Unity always draws last.
  • Unity 6000.0 players log "No Theme Style Sheet set to PanelSettings" once when the panels first open. The panels draw correctly; Unity 6000.5 doesn't log it.
  • Off in release builds, unless a playtest build opts in (section 9).

12. The Basics sample and the package's tests

The sample. In the Package Manager, select Proving Ground, open Samples and import Basics. Open its Basics scene and press Play; everything is built from plain shapes in code, and it reads no input of its own, so it works with either input system and any render pipeline.

  • F1, Showcase: a ring of shapes. Tune their speed, count, height, size, shape and colours; the buttons log an event, reverse the direction and pick new colours.
  • F1, Runner: press Run scripted batch (3 + 3). A runner laps the ring three times under each of two presets, "Basics Steady" and "Basics Twitchy" (made the first time), using RunBatch, then the comparison opens with the six laps selected: Twitchy is faster but stumbles; see whether that pays. Run one lap records a lap with the current values.
  • F2: counters (laps, stumbles), a timer and events from both.

The package's tests. The package includes its EditMode tests. To run them, add the package to the testables list in your project's Packages/manifest.json, then open Window › General › Test Runner:

"testables": [ "com.exaweft.provingground" ]

The tests use temporary folders and never touch your presets, runs or PlayerPrefs. Without that entry they aren't compiled, and they are never part of a build.
